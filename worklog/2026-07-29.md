## Overview

Back to building tools after the restructure. First of Wave 2 (the time cluster) and the one

## Today's Work

### 1. How It Differs From the Existing Timezone Tool

I already have a timezone tool, so I was clear about why this is a separate one rather than a
duplicate. The timezone tool converts *one specific moment* between zones — you give it a
timestamp. The world clock answers a different, everyday question: "what time is it *right
now* in New York / London / Tokyo?" — many cities at a glance, updating every second. Same
underlying `Intl` machinery, different job.

### 2. Building It

`/world-clock` shows a grid of city cards — eleven cities across the major regions, plus the
visitor's own local time if it isn't already in the list. Each card has the city name, a big
live clock, the date, the UTC offset, and a ☀️/🌙 indicator.

Two `Intl` details I had to get right and verified in isolation before trusting them:

- **UTC offset**: `Intl.DateTimeFormat` with `timeZoneName: "shortOffset"` and pulling the
  `timeZoneName` part gives "GMT+8", "GMT-5", "GMT+5:30" — and it respects DST automatically
  (Sydney showed GMT+11 for a January date, since that's the southern-hemisphere summer). No
  hand-rolled offset math.
- **Day/night**: read the zone's current hour and treat 6:00–18:00 as day. The trap was
  midnight — a 2-digit 24-hour format can render "24" for 00:00, so I take the hour mod 24.
  Verified 00:00 UTC gives 0, not 24.

### 3. The Live-Time / SSR Tension, Handled Better Than Before

A live clock is client-only by nature — rendering `Date.now()` on the server would mismatch
on hydration. My first pass gated the *entire* grid on "mounted yet?", showing a placeholder
until the client took over. That worked, but I caught a flaw when I checked the shipped HTML:
the city names weren't in the server-rendered output at all, only after JS ran — bad for SEO
and no-JS users on a page whose whole point is those cities.

The fix was to split what's actually time-dependent from what isn't. City labels, layout and
structure render on the server; only the *values* — the ticking time, date, offset, day/night
icon — wait for the client, showing a `--:--:--` placeholder until then. Same hydration
safety (server and client both render the placeholder initially), but now the content is in
the HTML. Confirmed the city names are server-rendered in both locales.

A tick every second via `setInterval`, cleaned up on unmount; state updates wrapped in a
named function inside the effect, per the lint rule I've hit enough times to write from
memory now.

### 4. Verification

Unit-tested the offset and hour helpers across eight zones (including the India half-hour
offset and the midnight edge), lint + build (47 static pages), and served both locales: city
labels present server-side, placeholder shown pre-hydration, no English city names leaking
into the Chinese page, and the tool appears under the Time category and on `/tools`.

## Outcome

Wave 2 is underway with the world clock — the feature that motivated this phase. The useful
lesson was a refinement of a rule I already knew: "client-only for anything time-based" is
too blunt. Only the *value* is time-based; the surrounding content can and should render on
the server. Splitting the two kept the SEO without reintroducing a hydration mismatch.
