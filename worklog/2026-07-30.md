# Work Log · July 30, 2026 (Thursday)

**Hours:** ~4.5

## Overview

Second tool of Wave 2: a timezone meeting planner. The world clock answers "what time is it
there now?"; this one answers the harder scheduling question — "when can people in different
cities *all* meet during working hours?" It's the most involved UI of the wave, and the
logic needed real verification.

## Today's Work

### 1. The Model

The core idea: walk a full 24-hour day as a set of absolute instants (UTC midnight + 0…23
hours), and for each instant compute the local hour in every selected city. A row (instant)
is a viable meeting slot if *every* city's local hour falls inside the working-hours range.
Because time-zone offsets are effectively fixed day to day, any 24-hour window surfaces the
same overlaps, so anchoring to UTC midnight is enough — no need to reason about which
calendar day it is in each city.

Controls: a working-hours range (two selects, default 9:00–18:00), and an add/remove list of
cities from a curated set of sixteen spanning Honolulu to Auckland. The grid is a table —
columns are the chosen cities, 24 rows are the hours — with each cell colored by state
(working = green, awake, or asleep) and rows where *everyone* is working highlighted as the
answer.

### 2. Verifying the Logic Before the UI

This is the kind of tool that looks right and is subtly wrong, so I tested the overlap finder
in isolation first:

- LA / London / Beijing on 9–18: **zero** overlaps — correct, those three are too spread out
  to share a business-hours slot, which is exactly the real-world frustration this tool
  exists to reveal.
- Widen to 6–22 and one slot appears.
- New York / London on 9–18: the overlaps come out as NY 09–12 = London 14–17 — the genuine
  "morning in New York, afternoon in London" window anyone who's scheduled such a call knows.
- A single city on 9–18 yields nine hours.

Having those four results match my expectations gave me confidence the coloring and
highlighting in the UI were reflecting real math, not a plausible-looking bug.

### 3. Applying Yesterday's SSR Lesson

The grid depends on today's date (via the instants), so it's client-only — same category of
problem as the world clock. I applied yesterday's refinement from the start this time: the
**city column headers and the controls render on the server** (so the page has real content
and the city names are in the HTML), while only the **time grid** waits for the client. No
first-pass "gate the whole thing" mistake to walk back today. Confirmed the default city
headers are server-rendered in both locales.

### 4. Verification

Lint + build (49 static pages), and served both locales: default cities and controls present
server-side, no English strings leaking into the Chinese page, the tool listed under Time and
on `/tools`, and search finds it — including the nice detail that the Chinese query 时区
(timezone) surfaces *both* the timezone converter and the meeting planner, since both
descriptions use the word.
