# Work Log · August 14, 2026 (Friday)

**Hours:** ~4.5

## Overview

The heaviest tool of Wave 5, and it opens a new category: an image compressor/resizer. Drop in
an image, pick a max width, quality and output format (JPEG / WebP / PNG), and download a
smaller re-encoded version — all in the browser, nothing uploaded. It introduces the **Image**
category, the eighth on the site.

## Today's Work

### 1. Fully Client-Side Image Processing

The whole pipeline runs on the client via the File and Canvas APIs, which fits ToolNest's
"nothing leaves your device" promise perfectly — the image genuinely never touches a server.
Load the file into an `Image`, draw it onto a `<canvas>` scaled to the target width (never
upscaling — `scale = min(1, maxWidth / originalWidth)` preserves the aspect ratio), then
`canvas.toBlob(…, mime, quality)` to re-encode. Quality applies to JPEG and WebP; PNG is
lossless so the quality control hides for it. The result shows original vs. compressed
dimensions and file size, the percentage saved, and a download link.

### 2. The Real Work: Object-URL Lifecycle

The subtle part wasn't the canvas, it was **memory management around `URL.createObjectURL`**.
Every re-encode creates a new blob URL, and every reasonable interaction (dragging the quality
slider, switching format) triggers a re-encode. Without care that leaks a blob per keystroke.
So I keep the current URL in a ref and revoke the previous one before assigning a new one, and
revoke the last one on unmount. I also load the source file through a temporary object URL that
gets revoked as soon as the `Image` has decoded. Same discipline as closing files.

### 3. Async + Effects, Carefully

`toBlob` is asynchronous, and the re-encode runs in an effect keyed on the source and all three
options. That's the same `cancelled`-flag pattern I've used for the async tools before (hash,
QR): if the options change again before a `toBlob` callback fires, the stale result is dropped
rather than clobbering the newer one. State updates live in the callback, not the effect body,
so they stay clear of the lint rule.

### 4. Verification and Its Limits

I was honest with myself about what I can and can't verify headlessly. The canvas encode needs
a real browser with a real file, which the terminal checks can't drive — so what I verified was
everything *around* it: lint, a clean build (77 static pages), both locales rendering the
upload UI and controls with no leakage, the new Image category showing on the home overview and
its own page, the sitemap picking up `/c/image` and the tool, and search finding it. The
processing code itself is standard File/Canvas usage with the URL lifecycle handled; it'll get
a real-file smoke test in the browser before I'd call it battle-tested.

## Outcome

Wave 5 is complete, and with it a big catch-up run. The site now spans eight categories,
including Image. The lasting lesson from this one is unglamorous but real: browser resource
handles — object URLs — need the same open/close discipline as files, or an innocent slider
turns into a memory leak.
