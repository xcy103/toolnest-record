# Work Log · July 24, 2026 (Friday)

**Hours:** ~4.5

## Overview

The last tool of Wave 1: a number base converter (binary / octal / decimal / hex, plus a
custom base up to 36). With it shipped, Wave 1 is complete and the library stands at twelve
tools — the threshold I set for pausing new tools and restructuring the front end. Short
build, but it turned up a genuine correctness trap and a project-config change.

## Today's Work

### 1. Design: Every Field Live, No "Convert" Button

Like the case converter, I skipped the from/to dropdown. There are four fields — binary,
octal, decimal, hex — plus a custom-base row; edit any one and the others update instantly.
A single BigInt holds the value; each field renders from it, except the field you're
currently typing in, which shows your raw text so it isn't reformatted mid-keystroke (the
same source-of-truth pattern as the timezone tool).

### 2. The Correctness Trap: Precision

The obvious implementation is `parseInt(x, fromBase)` then `Number.toString(toBase)`. It
works right up until it silently doesn't: JavaScript numbers are IEEE-754 doubles, exact
only up to 2^53. Convert a 64-bit hex value like `FFFFFFFFFFFFFFFF` and `Number` rounds it
to the wrong integer without any error.

So the whole tool is built on **BigInt**, which is arbitrary-precision. `BigInt.toString(radix)`
handles formatting for bases 2–36; for parsing I wrote a small digit-by-digit loop
(`value = value * base + digit`) since BigInt has no arbitrary-radix parse. I verified the
precision point explicitly: `2^53 + 1` (9007199254740993) round-trips dec → hex → dec
exactly, whereas `Number` would report 9007199254740992. Also checked negatives, base-36
(`zz` → 1295), empty input, and invalid digits per base (`102` in binary → error on that
field only).

### 3. A Config Change: ES2020

Writing the BigInt literal `0n` broke the type check: "BigInt literals are not available
when targeting lower than ES2020." The project's `tsconfig` still had the scaffold default
`target: "ES2017"`. Since BigInt genuinely is an ES2020 feature and every browser the site
targets has supported it for years, the right fix was to bump the target to **ES2020** rather
than work around the literal. Rebuilt clean. Good moment to retire a stale default.

### 4. Verification

Unit-tested the parse/format pair (standard bases, custom base, negatives, precision,
invalid input), then lint + build (31 static pages) and served both locales: the tool
renders with translated labels, invalid digits flag only the offending field, and it shows
up under the Developer category on both home pages.

## Outcome

**Wave 1 is done — twelve tools live** across six categories. The recurring theme of this
wave held to the end: the "simple" tools each hid one real subtlety — unbiased randomness,
bilingual word counting, style-aware tokenizing, and today, integer precision. Building each
one properly rather than reaching for the naive version is what makes the set trustworthy.

## Next

No new tool next. The library is big enough that the home page is getting long, so the plan
now is the **front-end restructure**: category navigation in the navbar, per-category pages
at `/[locale]/c/<category>`, a client-side search, and a slimmer home page — so the site
stays browsable as it keeps growing.
