# Work Log · August 28, 2026 (Friday)

**Hours:** ~4.5

## Overview

Today's task was the **JSON ↔ YAML converter**, the biggest remaining data-format item in the
backlog. It converts JSON into readable YAML, and parses YAML back into formatted JSON. Unlike CSV,
this is not a format I should hand-roll, so the main decision was to use a mature YAML parser and
make the supported scope clear. This brings ToolNest to 33 tools.

## Today's Work

### 1. Choosing a Library Instead of Writing a Parser

YAML looks friendly, but it is not simple: indentation matters, scalars have typing rules, there
can be comments, anchors, aliases and multiple documents in one file. A hand-written parser would
either be incomplete in quiet ways or take far too much time away from building the product.

Installed `yaml@2.9.0`, a browser-compatible library with no external dependencies. I read the
package README and used its documented `stringify` and `parseAllDocuments` APIs. That keeps the
tool honest: ToolNest owns the UI and product behaviour, while the actual YAML grammar is handled
by code built for that job.

### 2. Scope: One YAML Document

The page supports one YAML document at a time. That maps cleanly to a single JSON value. Multi-doc
YAML streams are valid YAML, but they do not have one obvious JSON output unless I invent a wrapper
array or a special convention. I chose not to do that. If the input has more than one document, the
tool reports a clear error instead of guessing.

Advanced YAML features are still parsed by the library, but the output is ordinary JSON values.
That scope is stated directly on the page so the user knows this is a converter, not a YAML editor.

### 3. Library Module and Tests

Added `lib/json-yaml.ts` with two functions: `jsonToYaml` and `yamlToJson`. The module catches
syntax errors and turns them into error identifiers (`invalidJson`, `invalidYaml`, `multipleDocs`,
`unsupported`) so the page can translate the message into English or Chinese.

Testing caught a useful detail. My first attempt used `parseDocument`, but a multi-document input
was reported as a YAML syntax error before my own "one document only" rule could fire. Switching to
`parseAllDocuments` let the code count documents first, then validate the single document. That is
exactly why the pure library test belongs before the UI.

The tests cover:

- JSON object/array output as readable YAML.
- YAML mappings and sequences back to formatted JSON.
- 2-space and 4-space indentation.
- Invalid JSON.
- Invalid YAML.
- Multi-document YAML rejection.

### 4. Page and Wiring

Built `/json-yaml` as a bilingual Client Component with direction tabs, indentation controls,
example input, input/output panels and copy support. Added the per-tool layout for metadata and
JSON-LD, registered the tool in `lib/tools.ts`, and added English/Chinese messages. Because the
site's registry drives navigation, the new page appears automatically in the Developer category,
the full `/tools` page, search and the sitemap.

### 5. Verification

Ran the full checks:

Then served the production build locally and checked `/en/json-yaml`, `/zh/json-yaml` and

## Outcome

right engineering move is not to prove I can parse a format, but to know when the format deserves a
real parser and to build the product surface around it carefully.
