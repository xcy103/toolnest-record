## Today's Work

### 1. Writing a Privacy Page Means Auditing the Site

I expected this to be the easy half of the day and it was the interesting one. A privacy
statement is only worth writing if every sentence is true, so before writing anything I went
looking for what the site *actually* does.

Two findings I would have got wrong from memory:

- **There is a cookie.** I would have written "no cookies at all". But next-intl's locale
  negotiation sets `NEXT_LOCALE` on the redirect from `/` — I confirmed it with a request and
  read the `Set-Cookie` header myself: `NEXT_LOCALE=en; Path=/; SameSite=lax`. It's purely
  functional, but it exists, and the page says so by name.
- **Fonts are not fetched from Google at runtime.** The site uses `next/font`, which downloads
  the font files at build time and serves them from the site's own origin. I checked the built
  HTML for outbound hosts: the only external URLs on a page are the GitHub link, the
  schema.org identifier inside the JSON-LD (which isn't fetched), and the site's own canonical.
  So "opening a page contacts no one but the host" is a claim I can stand behind.

The rest was easy to verify: no analytics package in `package.json`, no ad or social scripts,
`localStorage` used exactly once for the light/dark preference, and no server code that could
receive user input. I also said plainly that the host (Vercel) processes IPs and user agents
like any web host — a privacy page that pretends the network layer doesn't exist isn't honest.
And I put in a commitment: if a tool ever needs a server, this page changes *before* that ships.

That last line has a practical consequence I noted in the roadmap — adding analytics is now a
documented promise to break, not a small convenience.

### 2. The About Page

Shorter: what ToolNest is (a tool collection and the company's site), the four principles it's
built on (runs locally, free without an account, small and fast, bilingual), how it's built, and
a link to the source. The tool and category counts come from the registry rather than being
typed in, so they can't drift — the page already says 28 tools and 8 categories without me
touching it.

### 3. Reusing What Exists

Neither page needed new layout code. `ToolLayout` and `ToolPanel` already give the breadcrumb,
heading and card sections, and — because they're plain Server Components using next-intl's
`useTranslations` — they drop straight into a static page. Both pages are Server Components, so
unlike the tool pages they can export `generateMetadata` directly, using the section helper I
wrote on Monday.

Wiring: both added to the footer (which now wraps properly on narrow screens), both in the
sitemap with the usual hreflang pair, both bilingual. One nit fixed afterwards — the About tab
read "About ToolNest · ToolNest", so the metadata title is now just "About" while the heading
keeps the fuller name. 85 static pages, lint and types clean.

The roadmap file calls itself a living plan and had been standing still since July 18. It now
marks all five waves and the navigation restructure as done with their dates, adds an
"After Phase 3" section covering this week's SEO pass, JSON ↔ CSV, find & replace and today's
pages, strikes through the backlog items that exist, and lists what's genuinely still open:
the deferred image-tool browser test, the custom domain, and the next backlog candidates.

found a cookie I didn't know I was setting, and that's exactly the kind of small untruth these
pages usually carry.
