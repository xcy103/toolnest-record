# Work Log · August 3, 2026 (Monday)

**Hours:** ~4.5

## Overview

Start of a new week and the first tool of Wave 3, the developer batch: a JWT decoder. It
shows the header and payload of a JSON Web Token, decoded entirely in the browser. A focused
tool, but a good one to lead the wave — JWTs are everywhere in web development and people
constantly need to peek inside one.

## Today's Work

### 1. What It Does — and Deliberately Doesn't

A JWT is three base64url-encoded parts joined by dots: `header.payload.signature`. The
header and payload are just base64-encoded JSON — not encrypted, only encoded — so anyone
can read them. The signature is a keyed hash that proves the token wasn't tampered with.

The important design decision was to **decode, not verify**. Verifying the signature needs
the secret or public key, and a browser tool that asked users to paste their signing secret
would be teaching a bad habit. So this tool splits the token, decodes the header and payload,
and pretty-prints them — and says plainly, right on the page, that the signature is *not*
verified. That's the honest scope for a client-side decoder, and it matches what the
well-known JWT tools do.

### 2. Decoding base64url (Not Plain base64)

The one real gotcha: JWTs use **base64url**, not standard base64. Two characters differ (`-`
and `_` instead of `+` and `/`), and the `=` padding is stripped. So before handing it to
`atob` I translate those characters back and re-add the right amount of padding. Then, as
with the Base64 tool weeks ago, I decode through UTF-8 bytes so tokens with non-ASCII claims
(a Chinese name, say) come out correctly rather than as mojibake.

### 3. A Small Useful Touch: Human-Readable Timestamps

JWT payloads carry timestamps — `iat` (issued at), `exp` (expires), `nbf` (not before) — as
Unix seconds, which are unreadable at a glance. When those claims are present I show them
formatted as real dates in the visitor's locale, below the payload. It's the difference
between "exp: 1735689600" and "exp · Expires at: Jan 1, 2025" — the thing you actually wanted
to know.

### 4. Verifying Before Building

Tested the decoder in isolation first, as usual: the canonical example token (the "John Doe"
one from the JWT docs) decoded to exactly the expected header and payload; a token I built
with a Chinese name in the payload round-tripped correctly through the UTF-8 path; and
malformed inputs — one part, empty, junk — all threw rather than producing garbage, so the
friendly error message fires.

### 5. Verification

Lint + build (53 static pages now), served both locales: the page renders with translated
labels and the "not verified" caveat, no English leaks into the Chinese page, the tool shows
under the Developer category and on `/tools`, and search finds it (in Chinese, 解码 nicely
surfaces the Base64, URL and JWT tools together, since all three decode something).

rather than reach for signature verification that doesn't belong in a no-backend browser tool.
