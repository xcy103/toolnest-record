## Overview

what to put in its place, and get the result — literal or regular expression, optionally case

the sixth in the Text category.

## Today's Work

### 1. The Part That Looks Trivial and Isn't

"Replace all occurrences" is one JavaScript call, which is exactly why it's worth slowing down.
`String.replace` with a global regex does the work, but three details decide whether the tool is
correct or quietly wrong:

**Literal mode has to be genuinely literal.** If the user searches for `$5.00`, the `$` and `.`
are regex metacharacters — an unescaped search would match "35100" and miss the actual price.
So literal mode escapes every metacharacter before building the pattern. The test I care about
most: searching `.` in `a.c abc` replaces exactly one character, not four.

**The replacement string has special syntax too.** In `String.replace`, `$&` means the whole
match and `$1` a capture group. That's a feature in regex mode and a bug in literal mode — a
user replacing a word with `$&` wants those two characters, not a copy of the match. So the
replacement gets its dollars doubled (`$$`) when regex mode is off, and passed through untouched
when it's on.

**Zero-length matches still bite.** I met this in the regex tester and met it again: a pattern
like `x*` matches the empty string between every character, so counting matches with an
`exec` loop hangs unless `lastIndex` is nudged forward by hand. `"abc"` with `x*` → 4 matches
and the output `-a-b-c-`, which is what a text editor does too.

Whole-word mode wraps the pattern in `\b(?:…)\b`. The non-capturing group matters: without it,
`cat|dog` becomes `\bcat|dog\b`, and alternation binds loosest, so only the first alternative
would get the leading boundary.

### 2. Library, Then UI

`lib/replace.ts` exports the small pieces — `escapeLiteral`, `buildPattern`, `findMatches`,
`replaceAll` — and throws `invalidPattern` (carrying the engine's own message) when the user is
mid-way through typing a regex. 19 tests before any UI existed, covering all of the above plus
case sensitivity, `$1`/`$&` group references, punctuation neighbours in whole-word mode, and a
multi-line replacement.

I deliberately did **not** interpret escape sequences in the replacement field: `\n` stays a
backslash and an n. The replacement box is a real input and a newline can be pasted into it, so
inventing a mini-language would only surprise people who genuinely want a backslash.

### 3. Preview

The page shows a highlighted preview of the source with every match marked before replacing, which
is the difference between "hope this regex is right" and seeing that it is. That reuses the
`<mark>` approach from the regex tester, with the zero-length matches skipped since there's
nothing to paint.

## Outcome

28 tools. Today's keeper: the difference between *searching* for text and *matching* it. Two
strings that look identical behave differently the moment one of them is compiled as a pattern,
and a find & replace tool is exactly where that difference does damage — so escaping, in both
directions, is the whole job.
