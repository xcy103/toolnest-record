## Overview

Last tool of Wave 2: a combined countdown and date-difference tool. Two modes — count down
live to a future moment, or measure the span between two dates as calendar years/months/days.
It looked like the simplest tool of the wave and turned out to hide the nastiest bug, which
is becoming a familiar pattern with anything involving dates.

## Today's Work

### 1. Two Modes, Two Kinds of Time Math

- **Countdown** takes a target date-time and shows days/hours/minutes/seconds remaining,
  ticking every second. If the target is in the past it flips to counting *elapsed* time, so
  it's useful for "time since" as well as "time until". This is the live, client-only part.
- **Date difference** takes two dates and reports the duration both as a calendar breakdown
  (years, months, days) and as totals (days, weeks). It's order-independent — put the dates
  in either way round.

### 2. Parsing Dates as Local, Not UTC

A small trap I knew to avoid from the timezone work: `new Date("2026-07-31")` parses a
date-only string as **UTC** midnight, which then displays as the *previous* day for anyone
west of Greenwich. So the difference mode parses the `<input type="date">` value by hand into
a local-midnight `Date`. The countdown's `datetime-local` value, by contrast, is already
local, so `new Date(value)` is correct there — different input types, different rules.

### 3. The Bug: Negative Days in the Calendar Breakdown

Calendar year/month/day math is deceptively hard, so I tested it in isolation before wiring
the UI — and the first version was wrong. From **Jan 31 to Mar 1** it reported "1 month
**−2** days". Negative days is nonsense.

The cause was the borrow step. When the day-of-month goes negative you borrow a month's worth
of days — but my first version borrowed the length of the month *before* the end date
(February, 28 days). Starting from Jan **31**, 31 is already more than 28, so the borrow
didn't cover it and left days negative. The fix is to borrow the length of the *start
date's* month instead, which is always at least the start day-of-month, so the result can
never go negative. I proved that to myself and re-tested: Jan 31 → Mar 1 is now "1 month 1
day" (29 days total), and a battery of cases — month-end boundaries, a leap-day span, a
36-year span, year rollovers — all come out sensible with no negatives.

Calendar differences are genuinely convention-dependent (there's no single "right" answer for
Jan 31 + 1 month), but the important properties are that it's self-consistent and never
produces an impossible value like negative days.

### 4. Verification

Unit-tested the calendar diff across nine date pairs, lint + build (51 static pages now),
and served both locales: both modes render with translated labels, no English leaking into
the Chinese page, the tool is under Time (which now correctly reads "4 tools") and on
`/tools`, and search finds it in both languages.
