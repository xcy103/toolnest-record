## Today's Work

### 1. Shared, Verified Encoding Path

Replaced the compressor's independent canvas callback with the shared image encoder used by the
newer image tools. Browser output must now match the requested PNG, JPEG or WebP MIME type; a
silent fallback is reported as an export error instead of being offered with the wrong extension.

Maximum-width calculations preserve the original ratio and never enlarge a smaller source.
JPEG export now has an explicit background colour, and filenames use the original basename plus
`-compressed` and the correct `.jpg`, `.png` or `.webp` extension.

### 2. Input and Asynchronous Safety

The page now accepts only PNG, JPEG and WebP, limits files to 20 MB, and enforces the shared
8192-pixel-side and 16,777,216-pixel canvas limits after decoding. Unsupported, oversized,
corrupt and failed-export cases have localized errors.

Changing files, width, quality, format or JPEG background clears the old download immediately.
Generation tokens prevent stale asynchronous results from returning, and every replaced object
URL is revoked. Processing status is exposed while a new result is being encoded.

### 3. Real-File and Responsive Verification

A generated, non-personal 1600 × 1000 high-entropy PNG was processed in the browser. The 4.59 MB
source, set to a 600-pixel maximum width and 50% JPEG quality, produced a 600 × 375, 33.3 KB result
and reported a 99% reduction. The download name was
`toolnest-compressor-fixture-compressed.jpg`.

A corrupt file named as PNG showed the translated decoding error and removed the previous result.
At a 390 × 844 mobile viewport, document and viewport widths both measured 390 pixels, with no
horizontal overflow.

## Learning Notes

The reliability pass demonstrates why browser file tools need both declared-type validation and
post-encode MIME checks, plus explicit cancellation and object-URL ownership. A measured output
dimension and independently visible file size are stronger evidence than a headless canvas assumption.
