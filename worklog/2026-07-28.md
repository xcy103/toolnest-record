## Overview

Second and final day of the front-end restructure. Yesterday added category pages and a

that's a proper landing page instead of a wall of every tool. With this the site scales:

## Today's Work

### 1. Client-Side Search

The search is the piece that matters most as the library grows. Because everything about a
tool that's worth searching — its name and description — lives in the message catalogues, a
search has to run against the *translated* strings, and it has to match the language the
visitor is actually reading.

I built it as a client component (`ToolDirectory`) that filters the registry live: for each
tool it pulls the localized name and description via `useTranslations` and matches the query
against those plus the slug. No backend, no index — instant filtering over twelve tools, and
it stays correct in both languages (I checked that "base" finds both Base64 and the base
converter in English, and that 密码 / 进制 / 二维码 find the right tools in Chinese).

### 2. Home as a Landing Page

The home page used to dump every tool grouped by category — fine at six tools, too long at
twelve, unworkable at thirty. I split it:

- **Home** is now hero + search + a **category overview**: one card per category showing its
  name, a few tool icons, and a live count, each linking to that category's page. It answers
  "what kinds of things are here?" at a glance instead of making you scroll past everything.
- The full grouped directory moved to a dedicated **`/tools`** page (the old home content,
  essentially), with its own title and metadata.

The `ToolDirectory` component ties search and overview together: empty query shows the
category overview, a query swaps it for matching tool cards (or a "no matches" message). One
component, one place, both states.

### 3. A Discoverability Gap I Caught in Testing

When I verified the pages, the `/tools` page was only reachable two ways: the navbar dropdown
(which renders its links only when opened, so they're not in the initial HTML) and the
sitemap. That meant a visitor with JavaScript disabled, or a crawler not following the
sitemap, had no visible path to the full list. So I added a "View all →" link next to the
"Browse by category" heading — a plain link, present in the static HTML. Confirmed it shows
up server-rendered in both locales. Small thing, but the kind of gap that's invisible until
you actually check what's in the shipped HTML rather than what you intended.

### 4. Verification

Unit-tested the filter against the real message files (English and Chinese queries), then
lint + build (45 static pages). Served the build and confirmed: the home page is slim
(search + overview, not every tool), `/tools` lists all twelve, the sitemap now carries home
+ `/tools` + six categories + twelve tools (20 URLs), and the "View all" link is present in
the static HTML.

## Outcome

The front-end restructure is done. The site is navigable three ways now — search for a
specific tool, jump to a category from the navbar or the home overview, or browse everything
on `/tools` — and the home page is a landing page rather than a scroll. The structure will
hold as the tool count keeps climbing, which was the whole point of pausing to build it.
